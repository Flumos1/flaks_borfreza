# Проверка сайта borfrezy.in.ua, 23 сентября 2026

## Merchant Center

На предоставленном скриншоте: «Пользователь не может завершить покупку», срок исправления 28 сентября 2026. Это предупреждение касается всего аккаунта. Скриншот не раскрывает конкретный запрос или этап, на котором проверка Google не прошла.

На рабочем сайте проверен переход со страницы товара в корзину: кнопка покупки уже работала, минимальной суммы заказа не было. Найденные пробелы: отсутствовал выбор оплаты и отделения/адреса доставки, email был обязательным, в корзине не показывался артикул. Эти пробелы исправлены. Способы оплаты взяты из существующей страницы доставки: при получении и по счёту.

Снятие предупреждения не подтверждено. Google отклоняет сохранённый refresh token с `invalid_grant`; требуется повторный вход владельца. Скрипт диагностики переведён с устаревшего Content API на Merchant API v1, добавлены ошибки аккаунта и явное отображение ошибок чтения API. Новый API ещё не проверен на реальном аккаунте; в проекте Google Cloud должен быть включён `merchantapi.googleapis.com` и выполнены требования регистрации разработчика Google, если API их запросит.

## Исправления

- Оформление: адрес/отделение Новой Почты, выбор оплаты, необязательный email, артикул и цена за единицу; эти данные передаются менеджеру.
- API: обязательная проверка имени, телефона, доставки и оплаты; JSON и ограничение размера запроса; точный список разрешённых источников вместо всех `*.vercel.app`; цена только из серверного каталога.
- Корзина: ограничение количества остатком из каталога; сохранение при неудачной отправке; закрытая корзина недоступна по Tab, открытая удерживает фокус; управление Escape; удобная единая прокрутка на телефоне.
- Уведомления: Telegram и email отправляются параллельно, запросы ограничены по времени; успех только при успешной доставке хотя бы в один канал. Детали ошибок провайдеров не выдаются покупателю.
- Наличие: фид, страницы, кнопки покупки и API используют общий источник данных. Остатки в каталоге статические; автоматического складского учёта в проекте нет.
- SEO: canonical и og:url обновляются при смене языка. Товарные страницы уже содержат переведённый HTML, лишний JavaScript переключения языка удалён. Исправлена горизонтальная прокрутка на узком экране.
- Сборка автоматически обновляет товарные страницы, фид и sitemap, затем проверяет согласованность цен, наличия и URL.
- Обновлены уязвимые зависимости сборки `browserslist` и `baseline-browser-mapping`. Секреты, отчёты и файлы окружения исключены из Git.
- OAuth: повторная авторизация при отозванном токене, проверка `state`, ограничение ожидания входа и сетевых запросов.

## Проверки

- `npm test`: 6 тестов с проверками корзины, некорректных запросов, подмены цены, остатков, доставки и резервного канала уведомлений.
- `npm run build`: сборка и SEO-проверка проходят; 80 товаров, 16 форм, 204 URL в sitemap.
- `npm audit`: 0 известных уязвимостей после обновления зависимостей.
- `node scripts/check-live.mjs`: 160 товарных страниц UA/RU и 8 служебных URL, без обнаруженных ошибок загрузки, цены, наличия или ссылки покупки.
- Браузер: оформление UA/RU, оплата при получении/по счёту, изменение количества, перезагрузка, успешная отправка и отказ сервера. Проверены компьютер и мобильные размеры 390x844, 360x740.
- Уведомления в браузерных тестах имитировались локальным сервером `node tests/preview-server.mjs`. Реальные заказы не отправлялись; доставка уведомлений из production не подтверждена.

## Что требует владельца

1. Завершить вход Google для чтения текущего состояния Merchant Center. Команда: `node scripts/merchant-audit.mjs --authorize`.
2. Владелец подтвердил: доставку оплачивает покупатель по тарифам перевозчика. Условие добавлено в корзину, товарные страницы и страницу доставки на UA/RU; сумма товаров отделена от доставки. После восстановления доступа необходимо сверить настройки доставки в Merchant Center. Комиссия за наложенный платёж отдельно не уточнялась.
3. Подтвердить реальные остатки и условия возврата. Данные склада и бизнес-политики не проверяются по одному исходному коду.
4. Проверить получение контрольного заказа в production. Для полной защиты от прямого спама и повторной отправки при сетевых сбоях в перспективе нужны серверное хранилище заказов/идемпотентность и ограничение частоты запросов; один Origin не заменяет их.
